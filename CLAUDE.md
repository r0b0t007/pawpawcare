# PawPawCare

Pet health management app: **`frontend/`** is an Expo SDK 57 React Native app (React Navigation with `@react-navigation/native-stack` — not expo-router, not the JS stack; StyleSheet + design tokens in `frontend/src/theme/index.js` — not NativeWind; custom fetch client `frontend/src/services/api.js` with JWT auto-refresh; global store `frontend/src/context/DataContext.js`). UI follows the "Lively & Light" redesign (brief: `docs/redesign-prompt.md`; mockups: `design/lively/`) built on Direction 1g: use only the `ui`/`type`/`radii`/`PET_COLOR_PAIRS`/`petPair`/`elevation`/`scrim`/`photos` theme exports and the shared kit in `frontend/src/components/` (Card, ListRow, StatusRing, StatusPill, Chip, SegmentedControl, Button, Sheet, ConfirmDialog, Toast/showToast, UpNextCard, PetCard, PetFace, PetFaceStack, EmptyState, StepProgress, TextField, ScreenHeader, `reminderIcon`; shared formatting in `frontend/src/utils/dates.js` + `utils/pets.js`, daily-dose counting in `utils/doses.js`, `hooks/useToday.js` for anything keyed on "today" in a screen that stays mounted, and `hooks/useInFlight.js` to guard any save button against double taps; `DataContext` mutations resolve a truthy value on success and `false` on failure, so a screen confirms only what was actually saved) — one `#8a5300` accent for actions only, pet identity tints for pet surfaces (never actions), 1px borders everywhere except the ONE soft shadow level (`Card elevated` / `elevation`) on a screen's hero card, photo cards and a floating action, status rendered exactly once as icon + word, real photos (a user's pet photo always wins; Unsplash stock in `frontend/assets/images/` is decorative only — welcome, onboarding, empty states — never shown as the user's pet), one primary action per screen, deletes only behind ConfirmDialog. Motion (animate-expo pass): Reanimated 4 only (never core `Animated`), tokens in the theme's `motion` export + worklets/easings in `frontend/src/components/motion.js`, springs where a finger was involved, everything ≤300ms, reduced-motion respected, haptics only at the four moments listed in `SegmentedControl`/`Toast`/`Sheet`/`ConfirmDialog` — no confetti, no tab animations, no entrance staggers. **`backend/`** is a Laravel 13 REST API (JWT HS256 with refresh rotation, snake_case JSON, routes at root — no `/api` prefix).

## Commands

- Frontend: `cd frontend && npm test` (Jest), `npm start` (Expo dev server), `npm run build:dev|build:preview|build:prod` (EAS), `npm run update` (EAS Update), `npx expo-doctor`.
- Backend: `cd backend && composer dev` (serve + queue + logs), `php artisan test` (PHPUnit), Pint auto-formats PHP edits via hook.
- Versioning: `cd frontend && npm run version:patch|minor|major` (syncs app.json).
- Android E2E (LLM-driven, on a local emulator): `cd ../artemis && .\pawpaw-emulator.ps1`, then `uv run artemis run "<task>" --profile flash`. Complements Jest, never a CI gate; Android only. Full runbook + gotchas: `docs/android-e2e-testing.md`.
- API load testing (deterministic, k6): `docker compose -f loadtest/docker-compose.yml up --build -d`, then `docker compose -f loadtest/docker-compose.yml exec -T api php artisan loadtest:seed-users --count=500 --out=/loadtest/users.json --force` (**inside** the container — seeding from the host signs tokens with a different `SECRET_KEY` and every request 401s), then `k6 run loadtest/k6/smoke.js` and `k6 run loadtest/k6/breakpoint.js`. Measured 2026-09-20: **~250 req/s** at 20 fpm workers; `CACHE_STORE=database` is 2.5x worse than `file`; more workers does not help (CPU-bound). `down -v` between A/B configs or variance swamps the result. Never a CI gate, and **never aimed at production** (Namecheap's AUP forbids it, and CloudLinux's entry-process cap makes the numbers meaningless anyway — read the real ceiling from cPanel → Resource Usage). The target is nginx + php-fpm because `php artisan serve` is single-threaded. Auth routes are `throttle:20,1` per **IP** and `throttle:api` is 120/min per **user**, so tokens are pre-minted and load is spread over a seeded pool of ≥ peak_rps/2 users. Full runbook: `docs/load-testing.md`.

## Environments

- Production API: **https://api.pawpawcare.app** (Laravel on Namecheap cPanel — see `docs/deploy-backend.md`). Marketing site: **https://pawpawcare.app** (Cloudflare Pages, git-connected to this repo — deploys `website/` on push to `main`, root directory `website`, no build command; DNS is now on Cloudflare nameservers). Store/preview builds get the API URL from `eas.json` env; local dev uses `frontend/.env.local`. The **`e2e`** build (LLM-driven test runs) points at local Laravel on `http://10.0.2.2:8080` (the emulator's alias for the host loopback; 8080 because ARTEMIS owns 8000) so test runs never write to production. **`app.json` stays the static source of truth; `frontend/app.config.js` spreads it through unchanged and only layers on the `expo-build-properties` cleartext-HTTP opt-in when `ENVIRONMENT=e2e`** — never move `usesCleartextTraffic` into `app.json`, it is an app-wide manifest flag and would permit cleartext in production too. **Editing `frontend/eas.json` changes the runtime fingerprint** (the whole file is a fingerprint source), which cuts every installed app off from OTA updates until it is rebuilt — batch `eas.json` edits (the `e2e` profile, iOS submit credentials) with a native build round, and check `npx expo-updates fingerprint:generate --platform android` before and after.

## CI/CD

**GitHub Actions in `.github/workflows/` is the canonical CI/CD — do not create `.eas/workflows/`.** `ci.yml` (tests + a dependency audit job: `composer audit`, and `frontend/scripts/audit-deps.js`, which fails on high/critical npm advisories not in `frontend/audit-allowlist.json` — every allowlist entry needs a reason it can't reach users and a `review_by` date), `ota-update.yml` (EAS Update on main), `preview-build.yml` (preview branch), `production-release.yml` (version tags), `deploy-backend.yml` (SSH deploy of `backend/` to the cPanel host on merge to main — see `docs/deploy-backend.md` §7), `indexnow.yml` (pings IndexNow/Bing with changed `website/` URLs on merge to main; manual dispatch accepts a URL list), `deploy-website-cloudflare.yml` (manual-only `workflow_dispatch` CLI fallback deploy of `website/` to Cloudflare Pages via `wrangler` — Cloudflare's own Git integration does the real deploys on push, see `docs/deploy-website-cloudflare.md`). `.github/dependabot.yml` opens weekly PRs for composer, GitHub Actions and an **allowlist of pure-JS frontend packages only** — never add a package with native code to it (it changes the fingerprint `runtimeVersion` and cuts installed builds off from OTA; native packages move with SDK upgrades / EAS build rounds), and never add frontend `package.json` scripts casually (they're part of the fingerprint too). When editing the EAS steps in these workflows, consult the `expo:expo-cicd-workflows` skill for EAS CLI semantics only — output stays in GitHub Actions.

**Marketing site host migration — complete (2026-08-31):** `website/` moved from Netlify to Cloudflare Pages. The waitlist form runs as a Cloudflare Pages Function (`website/functions/api/waitlist.js`, Resend-backed) instead of Netlify Forms — **when editing `website/functions/`, remember `wrangler pages deploy` does not bundle it automatically; only Cloudflare's own git-integrated builds and `wrangler pages functions build` (used by `deploy-website-cloudflare.yml`) do.** `pawpawcare.app`'s DNS is now fully on Cloudflare (nameservers `braden`/`natasha.ns.cloudflare.com`); `api.pawpawcare.app` and mail records stayed DNS-only (unproxied) and are unaffected. ## React Query migration (in progress)

Data fetching is migrating from `DataContext` to `@tanstack/react-query`, one domain per PR. Pattern (pilot: pets / `PetsListScreen`):

1. Query keys live in `frontend/src/hooks/queryKeys.js`; domain hooks in `frontend/src/hooks/` (see `usePets.js`) reuse the `services/api.js` client and the mappers exported from `DataContext.js`.
2. **Reads** migrate to `useQuery`; **writes stay in `DataContext`** until every reader of that domain has migrated — DataContext mutations invalidate the matching query key to keep both stores in sync.
3. Screens refetch on focus via `useRefetchOnFocus` to pick up edits from unmigrated screens.
4. Consult `expo:expo-data-fetching` before extending. Migrated so far: pets (pilot), gamification (`useGamification.js` — reads-only domain), community groups (`useGroups.js` — the saved locale is part of the key, so a language switch is a new query; `toggleGroupMembership` writes the server's answer into the cache), invites (`useInvites.js` — `acceptInvite`/`declineInvite` drop the answered invite from the cache), lost pets (`useLostPets.js` — the board and my own reports; my reports left the sign-in load, so PetProfile offers neither report-lost nor mark-found until they load), community feed (`useFeed.js` — post, paw, report and comment answers are written into the cache; the feed is no longer a DataContext domain, so the full load lost a domain — Home's teaser still fetches it at sign-in through `useFeedCount`), notifications (`useNotifications.js` — the list and Home's bell (`useUnreadCount`); read/snooze/dismiss write the server's answer through `writeQueryCache`; `NotificationsRefresher` (App.js) re-reads it when a notification is shown or tapped and on foreground, and the reminder tick and full reloads re-read it too; the full load is now 2 domains, pets and reminders), medical vault (`useVault.js` — a pet's clinics, visits and documents together; re-read on every open and without retries; saves, deletes and AI reads write into it in the server's order, applying an AI reading re-reads it). Any query failing with `SESSION_EXPIRED` logs out once through DataContext's query-cache subscription (as `handleApiError` does), and `services/queryRetry.js` never retries it — query hooks need nothing of their own. A mutation that writes into a query's cache goes through DataContext's `writeQueryCache`: it cancels a fetch in flight (so an older answer can't undo the change) and then re-reads, re-reads when nothing is cached, and never turns a saved change into a failure. Queries whose mapper has translated fallbacks map the raw cache through `useLocaleSelect`. The full pet records (all six sub-resources) live in the cache under `petRecordsKeys`, fetched by their own query (`fetchPetRecords`/`petRecordsQuery` in DataContext: the sign-in load runs it, `usePetRecordsQuery` reads it — the Pets tab does, re-reading on focus once stale — and whichever starts first runs the one 1 + 6N load). Pet screens read them with `usePetRecords()` (hooks/usePetRecords.js: a store subscription that re-renders with each write and never starts a fetch) — `useData()` no longer exposes `pets`. **An exception to steps 2–3 above, by design:** a re-read of the records is a whole 1 + 6N load, so only the Pets tab re-reads them on focus (`usePetRecordsQuery`, once stale); the other pet screens follow the cache, which the sign-in load, full reloads and every mutation keep current — a co-owner's edit made on another phone shows after the next Pets-tab focus or reload; they are never garbage-collected and not retried. Their mutations write directly (`writePets`/`updatePetRecord`, on the current pet) rather than through `writeQueryCache`, by the owner's choice: cancelling would restart the whole 1 + 6N load, so a change made while the sign-in load or a full reload runs behaves as it always has. A change made while a screen's re-read runs (Pets tab focus, "Try again") does cancel it, write, then re-read. Full reloads after a server-side change (`loadData({ fresh: true })`: accepting a shared pet, applying a reading) cancel any older records fetch instead of joining it. The light `usePetsQuery` has no fetch of its own: the records load fills it from its `/pets` answer, for Home's early names. Remaining: reminders, **last** — DataContext's reminders list is also this device's notification schedule (`scheduleLocalReminders`, newest-request-wins, the post-fire refetch tick), so migrating its reads must keep one source for scheduling.
